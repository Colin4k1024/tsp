# TSP 平台瘦身计划

## 目标
识别当前平台中臃肿、冗余、孤立的能力，提出精简方案，同时为未来 `loop-engineer` 和 `graph-engineer` 角色预留空间。

---

## 一、现状总览

| 维度 | 数量 | 问题 |
|------|------|------|
| Skills 目录 | **204 个** (9.5MB, 1376 文件) | 34 个孤立、8 个 PUA 变体、1 个 6.4MB 巨物 |
| Commands | **87 个** | 6 个会话管理命令重叠、4 个命名冲突 |
| Specialist Agents | **27 个** | 16 个是语言特化变体（可参数化为 2 个） |
| Hooks | **46 个** (7 生命周期阶段) | 大量 inline JS 重复、功能门控 hook 装了但不激活 |
| Rules | **85 个文件** (13 语言目录) | 5 个语言目录 < 1KB，维护收益比低 |
| Runbooks | **178 个** | 大量 demo 脚本和窄领域安全门控文档 |
| Scripts | **190 个** | SQLite state store、skill-evolution 等重基础设施 |
| .grok-build/ | **2.6MB, 334 文件** | 生成产物被提交到仓库 |

## 二、瘦身清单（按优先级）

### P0 — 立即清理（零功能损失）

| # | 项目 | 大小 | 操作 |
|---|------|------|------|
| 1 | `skills/goframe-v2/` | **6.4MB, 962 文件** | 删除 `examples/` 和 `references/` 子目录（保留 SKILL.md 8KB）。或整体移至外部参考仓库。**单此项节省 67% skills 磁盘。** |
| 2 | `.grok-build/` | **2.6MB, 334 文件** | 加入 `.gitignore`，改为构建时生成。 |
| 3 | `skills/continuous-learning/` | 与 v2 完全相同 | 删除旧版，保留 `continuous-learning-v2`。 |
| 4 | `skills/autonomous-loops/` | 已声明废弃 | 删除。已被 `continuous-agent-loop` 替代。 |

**P0 预计节省：~9MB 磁盘 + 消除 2 个重复项。**

### P1 — 孤立能力清理（34 个 skill 不在任何 manifest module 中）

以下 skill 存在于磁盘但未被任何安装 profile 引用，属于死重：

```
agent-eval, agent-payment-x402, architecture-decision-records,
autonomous-agent-harness, benchmark, browser-qa, bun-runtime,
canary-watch, ck, click-path-audit, codebase-onboarding,
context-budget, design-system, documentation-lookup,
flutter-dart-code-review, gan-style-harness, git-workflow (715行!),
healthcare-cdss-patterns, healthcare-emr-patterns,
healthcare-eval-harness, healthcare-phi-compliance,
hexagonal-architecture, mcp-connector-bridge, nextjs-turbopack,
nuxt4-patterns, openclaw-persona-forge, opensource-pipeline,
product-lens, pytorch-patterns, repo-scan, rules-distill,
safety-guard, santa-method, skill-comply
```

**操作**：逐个决策——分配到合适的 module，或删除。建议：
- 保留并分配：`benchmark`, `browser-qa`(合并到 browser-smoke-testing), `git-workflow`, `hexagonal-architecture`, `pytorch-patterns`, `architecture-decision-records`
- 删除：其余 28 个（垂直领域 healthcare x4、niche 工具、重复功能）

### P2 — PUA 家族合并（8 → 1）

当前 8 个目录：
```
pua/ (77行) + pua-loop/ pua-mama/ pua-p10/ pua-p7/ pua-p9/ pua-pro/ pua-yes/ (各17-24行)
```

**操作**：将 7 个变体合并为 `pua/SKILL.md` 的模式参数段落。用 `/pua --mode=p7` 或 `/pua mama` 语法切换。减少 7 个目录。

### P3 — 语言特化 Agent 参数化（16 → 2）

当前 16 个语言特化 specialist agent：
- **10 个 reviewer**: cpp, go, java, kotlin, python, pytorch, rust, typescript, database, security
- **6 个 build-resolver**: cpp, go, java, kotlin, pytorch, rust

**操作**：参数化为 2 个基础 agent + 语言配置表：
- `reviewer.md` + `reviewer-languages.json`（每种语言的 lint/test/analyze 命令）
- `build-resolver.md` + `build-resolver-languages.json`

Agent 调用时传入 `language` 参数即可。减少 14 个文件。

### P4 — 会话管理命令合并（6 → 2）

| 当前 | 功能 | 合并为 |
|------|------|--------|
| `pause` + `save-session` | 暂停/保存 | `session` (子命令: save/resume/list) |
| `resume` + `resume-session` | 恢复 | ↑ |
| `sessions` | 管理 | ↑ |
| `checkpoint` | 检查点 | 保留（独立功能） |

### P5 — Hooks 瘦身

| 项目 | 操作 |
|------|------|
| Stop hooks 中 7 x ~2KB inline JS | 提取为独立 .js 文件，hooks.json 只引用路径 |
| `hooks/memory-persistence/` + `hooks/strategic-compact/` | 删除遗留兼容目录，统一到 `scripts/hooks/` |
| 功能门控 hooks (EVOLUTION/INSAITS/GOVERNANCE) | 不在对应 profile 中时，不安装到 hooks.json |
| `pre-bash-tmux-reminder.js` + `pre-bash-git-push-reminder.js` | 评估是否值得 hook 延迟，可能移至 session-start 提示 |

### P6 — Framework-Language 模块拆分

当前 `framework-language` 模块捆绑了 **35 个 skill**（Django + Laravel + Spring Boot + Kotlin + Perl + Swift + Go + Rust + Python + C++）。

**操作**：拆分为按语言的子模块：
```
lang-python, lang-golang, lang-rust, lang-kotlin, lang-java,
lang-swift, lang-perl, lang-php, lang-cpp, lang-csharp, lang-typescript
```
用户只安装自己使用的语言，避免为 35 个 skill 付费。

### P7 — Runbooks 精简（178 → ~80）

| 类别 | 数量 | 操作 |
|------|------|------|
| Demo 脚本 + 执行日志 | ~20 | 移至 `docs/examples/` |
| 每角色 daily-operations | 8 | 合并为 1 个 `role-operations.md` |
| 安全门控 runbooks | ~20 | 保留核心 5 个，其余移至 `docs/extras/security-gates/` |
| 对话示例 | ~8 | 移至 `docs/examples/conversations/` |
| 团队示例 | ~9 | 移至 `docs/examples/team-workflows/` |

### P8 — 命名冲突解决

| 冲突 | 操作 |
|------|------|
| `context-budget` (command + orphan skill) | 删除孤立 skill，保留 command |
| `harness-audit` (command + skill) | skill 是审计报告模板，command 是入口。保留两者但明确分工 |
| `pua` (command + skill) | 合并后自然解决 |
| `rules-distill` (command + orphan skill) | 删除孤立 skill，保留 command |

## 三、为 loop-engineer 和 graph-engineer 预留

### loop-engineer（Loop Engineering 基础设施已存在）

当前已有：
- `loop-state-store.js` — 目标中性的循环状态管理
- `loop-spec.js` — `.tsp/loop.yaml` 规范解析
- `heartbeat-scheduler.js` — 定时发现扫描
- `loop-operator` specialist agent — 验证循环编排
- `loop-engineering` manifest module

**需要新增**：
- `roles/loop-engineer/role.yaml` — 定义 loop-engineer 角色
- 能力范围：自动化循环任务设计、监控、收敛判断、异常升级
- 交接对象：tech-lead（升级）、qa-engineer（验证）、devops-engineer（运维）
- 推荐共享技能：`loop-heartbeat`, `systematic-debugging`, `eval-harness`, `continuous-agent-loop`

### graph-engineer（全新能力）

当前相关基础设施：
- CodeGraph MCP（符号/调用图分析）
- Graphify（结构扫描）
- GitNexus（跨仓图谱）
- `doc-updater` specialist（codemap 生成）

**需要新增**：
- `roles/graph-engineer/role.yaml` — 定义 graph-engineer 角色
- 能力范围：代码图谱构建、依赖分析、影响面评估、架构可视化、重构安全评估
- 交接对象：architect（架构决策）、frontend/backend-engineer（重构指引）、tech-lead（风险评估）
- 推荐共享技能：`codegraph`, `graphify`, `gitnexus`, `hexagonal-architecture`
- 新增命令：`/graph-impact`（影响面分析）、`/graph-visualize`（架构可视化）

## 五、执行顺序建议

1. **P0**（1 小时）：删除 goframe examples/references、gitignore .grok-build、删除重复 skill
2. **P1**（2 小时）：逐个决策 34 个孤立 skill
3. **P2**（1 小时）：PUA 合并
4. **P8**（30 分钟）：解决命名冲突
5. **P3**（2 小时）：Agent 参数化
6. **P4**（1 小时）：命令合并
7. **P5**（1 小时）：Hooks 提取和清理
8. **P6**（1 小时）：模块拆分
9. **P7**（2 小时）：Runbooks 重分类
10. **新增角色**（4 小时）：loop-engineer + graph-engineer 角色定义和配套

**总计约 16 小时工作量。**

### 风险与注意事项
- **P3 Agent 参数化**是改动最大的部分，需要修改 `team-skills-data.json` 和 `build-platform-artifacts.js`，需确保生成产物兼容现有安装流程
- **P6 模块拆分**会影响已安装用户的升级路径，需考虑迁移脚本或文档说明
- **P7 Runbooks 移动**会产生大量 git diff，建议单独 commit 便于 review
- **新增角色**需遵循 `roles/*/role.yaml` 的 schema，参考现有角色（如 `architect`）的结构

## 七、验证方式

每个 P 级别完成后执行：

1. `node scripts/validate-library.js` — 确保平台校验通过
2. `node scripts/validate-doc-freshness.js` — 确保文档一致性
3. `node scripts/build-platform-artifacts.js --check` — 确保生成产物最新
4. `node scripts/install-plan.js --profile team --target claude` — 验证安装计划无断裂引用
5. `node scripts/install-plan.js --profile full --target claude-code` — 验证 full profile 完整性
6. 手动检查：每个 manifest module 引用的 skill 目录都存在
7. 新增角色后：`node scripts/build-platform-artifacts.js` 重新生成，验证新角色的 agent/skill/command 产物正确生成
